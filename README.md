## 製品概要

### 背景(製品開発のきっかけ、課題等）

深夜、やるべきことを何もしないまま冷蔵庫を開けて、アイスを食べて後悔する。
開発者自身が何度も繰り返してきたことです。

ここで問題なのは「食べたこと」ではありません。**何もせずに食べて、後悔すること**です。
だから食べ物を取り上げても解決しません。食べられなかった夜に残るのは納得ではなく我慢で、
別の誘惑に逃げるだけです。

一方で、アプリの通知は無視できます。画面を閉じれば終わりです。
やるべきことを思い出させる仕組みは世の中にたくさんありますが、
**本当に手が伸びる瞬間に、避けようのない形で届くもの**がありません。

### 製品説明（具体的な製品の説明）

**その日の達成度が、冷蔵庫のドアの重さとして返ってくる冷蔵庫です。**

やるべきことを終えていれば、ドアはいつもどおり軽く開きます。
終えていなければ、開けるときに手応えがあります。

重要なのは、**開かなくはならない**ことです。この装置は食べることを禁止しません。
達成していなくてもドアは開きます。重いだけです。
食べるかどうかを決めるのは本人で、機械は判断しません。

仕組みとしては、冷蔵庫のドアを糸でBLDCモータの軸につないでいます。
モータが能動的にドアを閉めるのではなく、**人が開けようとしたときに、それに逆らう**。
FOC（ベクトル制御）で電流を指令することで、この「逆らう強さ」をソフトウェアから
連続的に設定できます。無通電なら軸は自由に回り、ドアは普通に開きます。

### 特長

#### 1. 禁止ではなく、手応えで伝える

ロックではありません。開くかどうかの2値ではなく、達成度に応じた段階的な重さです。
これはFOCで電流（＝トルク）を直接指令しているからできることで、
サーボや電磁ロックでは「中くらいの力で押し返す」が作れません。

#### 2. 通知と違って、無視できない

スマートフォンの通知は消せますが、手に触れる抵抗は消せません。
身体で受け取るフィードバックは、画面上のそれより確実に届きます。

#### 3. モータがアクチュエータであり、同時にセンサでもある

FOCは電流からユーザーが加えた力を読めます。
ホールセンサによる位置（24カウント/回転）と合わせて、
**ロードセルや角度センサを追加せずに**、いつ・どれだけの力で開けたかが記録できます。

### 解決出来ること

後悔そのものを消すことはできません。これは正直に書いておきます。

この装置がやっているのは、**食べたあとの後悔を、食べる前の躊躇に前倒しすること**です。
食べたあとの後悔は取り返しがつきませんが、食べる前の躊躇はまだ選べます。
「取り返しのつく後悔」に移し替えている、という整理です。

また、達成していない夜には、かえって罪悪感が増える可能性があります。
これは「何かを伝える機械は、悪い知らせも伝えてしまう」という構造的なもので、
回避する方法が見つかりませんでした。隠さず、設計上の論点として提出します。

### 今後の展望

- 既存のタスク管理ツール（Google カレンダー / Todoist 等）との連携
- PSOC™ Edge E84 AI Kit のカメラによる達成判定の自動化
  （現状は自己申告のため、申告の信頼性を上げる）
- 開閉ログの蓄積と可視化。「今週4回目です」を開ける前に見せる
- 冷蔵庫以外の誘惑（ゲーム機の収納、引き出し等）への展開

### 注力したこと（こだわり等）

* **「開かなくする」を選ばなかったこと。** 排除・ロック・罰としての設計は、
  実装が楽でデモも派手ですが、抜け道があれば一瞬で崩れ、何より本人の味方になりません。
  禁止せずに伝える、という一番難しい線を選びました。
* **停電やハングでドアが開かなくならないこと。** 無通電時はモータが自由に回るため、
  電源が切れればただのドアに戻ります。中に人や物が閉じ込められる構成にはしていません。
  ホストからのハートビートが止まったときもドライブを切ります。
* **「このキットでなければ作れないか」を最後まで疑ったこと。**
  2値のロックならサーボで足ります。段階的な力の指令にしたのは、
  FOCの必然性を立てるためでもあります。

## 開発技術

### 活用した技術

#### API・データ

* J-Link SWD によるオンチップメモリの直接読み書き（PyLink）
  ファームウェアの `door` 構造体をホストから読み書きし、MCUを走らせたまま
  指令とテレメトリをやり取りする。Infineon Motor Suite GUI と同じ方式

#### フレームワーク・ライブラリ・モジュール

* ModusToolbox™ / ModusToolbox™ Motor Suite（MCU側、C言語）
* PyLink（ホスト側、Python）

#### デバイス

* Infineon KIT_PSC3M5_MC1（PSOC™ Control C3M5 Complete System Motor Control Kit）
  * MCU: PSC3M5FDS2AFQ1 / Arm® Cortex®-M33、最大180MHz
  * DSP・FPU・CORDIC ハードウェアアクセラレータ
  * TCPWM + MOTIF（Motion Interface）ブロック
  * オンボードデバッガ SEGGER J-Link LITE
* Nanotec DB42S03 24V BLDCモータ（NEMA17、トルク定数 3.5 N·cm/A）
* KITMOTORDC250W24VTOBO1 パワーボード
* ホールセンサ（回転子位置検出、24カウント/回転）

### 独自技術

#### ハッカソンで開発した独自機能・技術

* **ドア抵抗制御ファームウェア** — [`motor-fw/door.c`](motor-fw/door.c) / [`motor-fw/door.h`](motor-fw/door.h)
  （commit `854a168`, `50266e7`）
  モータを「回す」のではなく「回されることに抵抗する」ために、
  ホール位置から開方向の動きを検出し、`level` に応じた電流を逆向きに流す。
  DISARMED / IDLE / RESIST / COOLDOWN の状態機械で、
  糸のたるみ取り、過速度、長時間の抵抗による発熱を管理している。

* **ホスト↔ファーム間のライブリンク** — [`host/door_link.py`](host/door_link.py)
  ELFからシンボルアドレスを解決し、J-Link経由で `door` 構造体を直接読み書きする。
  UARTを使わずにMCUを走らせたまま指令とテレメトリを扱える。
  ホストが心拍を送り続けないとドライブが切れるウォッチドッグを実装。

* **センサレスではなくホール位置検出を選んだこと**（commit `50266e7`）
  ドアを開ける動作はほぼゼロ速度域から始まるため、
  センサレスFOCでは回転子位置を推定できず保持トルクが出せない。
  SysTickでホールをサンプリングする構成に変更して解決した。
