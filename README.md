## 製品概要

### 背景(製品開発のきっかけ、課題等）

深夜、やるべきことを何もしないまま冷蔵庫を開けて、アイスを食べて後悔する。
開発者自身が何度も繰り返してきたことです。

ここで問題なのは「食べたこと」ではありません。**何もせずに食べて、後悔すること**です。
だから食べ物を取り上げても解決しません。食べられなかった夜に残るのは納得ではなく我慢で、
別の誘惑に逃げるだけです。

一方で、アプリの通知は無視できます。画面を閉じれば終わりです。
やるべきことを思い出させる仕組みは世の中にたくさんありますが、
**本当に手が伸びる瞬間に、避けようのない形で届くもの**がありません。

### 製品説明（具体的な製品の説明）

**その日の達成度が、冷蔵庫のドアの重さとして返ってくる冷蔵庫です。**

やるべきことを終えていれば、ドアはいつもどおり軽く開きます。
終えていなければ、開けるときに手応えがあります。

重要なのは、**開かなくはならない**ことです。この装置は食べることを禁止しません。
達成していなくてもドアは開きます。重いだけです。
食べるかどうかを決めるのは本人で、機械は判断しません。

仕組みとしては、冷蔵庫のドアを糸でBLDCモータの軸につないでいます。
モータが能動的にドアを閉めるのではなく、**人が開けようとしたときに、それに逆らう**。
FOC（ベクトル制御）で電流を指令することで、この「逆らう強さ」をソフトウェアから
連続的に設定できます。無通電なら軸は自由に回り、ドアは普通に開きます。

### 特長

#### 1. 禁止ではなく、手応えで伝える

ロックではありません。開くかどうかの2値ではなく、達成度に応じた段階的な重さです。
これはFOCで電流（＝トルク）を直接指令しているからできることで、
サーボや電磁ロックでは「中くらいの力で押し返す」が作れません。

#### 2. 通知と違って、無視できない

スマートフォンの通知は消せますが、手に触れる抵抗は消せません。
身体で受け取るフィードバックは、画面上のそれより確実に届きます。

#### 3. モータがアクチュエータであり、同時にセンサでもある

FOCは電流からユーザーが加えた力を読めます。
ホールセンサによる位置（24カウント/回転）と合わせて、
**ロードセルや角度センサを追加せずに**、いつ・どれだけの力で開けたかが記録できます。

#### 4. 「どれだけ食べたかったか」を測り、そのあとの気持ちと合わせて重さを変える

開けるたびに、手がモータに対してした仕事（ミリジュール）を記録します。
**欲しい気持ちの強さが、物理的な量として毎回残ります。** 画面をタップするだけのアプリには作れないデータです。

開け切ったあとには、画面が「食べてどうだった？（満足 / ふつう / 後悔）」と1タップで聞きます。
途中でやめた回は「我慢できた」として自動で残ります。
この記録から、時間帯ごとに最近の後悔が多ければ次から重く、満足が多ければ軽くします。
重さを一度決めて終わりではなく、**その人の「後悔するパターン」に合わせて重さが育っていく**ことが、
通知アプリや単純なロックとの違いです。

### 解決出来ること

後悔そのものを消すことはできません。これは正直に書いておきます。

この装置がやっているのは、**食べたあとの後悔を、食べる前の躊躇に前倒しすること**です。
食べたあとの後悔は取り返しがつきませんが、食べる前の躊躇はまだ選べます。
「取り返しのつく後悔」に移し替えている、という整理です。

また、達成していない夜には、かえって罪悪感が増える可能性があります。
これは「何かを伝える機械は、悪い知らせも伝えてしまう」という構造的なもので、
回避する方法が見つかりませんでした。隠さず、設計上の論点として提出します。

### 今後の展望

- 既存のタスク管理ツール（Google カレンダー / Todoist 等）との連携
- PSOC™ Edge E84 AI Kit のカメラによる達成判定の自動化
  （現状は自己申告のため、申告の信頼性を上げる）
- 開閉ログの蓄積と可視化。「今週4回目です」を開ける前に見せる
- 気持ちの記録を数週間ためて、後悔の割合・我慢できた回数・引いた力が、どう変わったかを見る。
  今の「時間帯ごとの単純な決まり」を、本人のデータから学ぶモデルに置き換える
- E84 のレーダーで「冷蔵庫の前に来たけど開けなかった」も数え、我慢の記録を正確にする
- 冷蔵庫以外の誘惑（ゲーム機の収納、引き出し等）への展開

### 注力したこと（こだわり等）

* **「開かなくする」を選ばなかったこと。** 排除・ロック・罰としての設計は、
  実装が楽でデモも派手ですが、抜け道があれば一瞬で崩れ、何より本人の味方になりません。
  禁止せずに伝える、という一番難しい線を選びました。
* **停電やハングでドアが開かなくならないこと。** 無通電時はモータが自由に回るため、
  電源が切れればただのドアに戻ります。中に人や物が閉じ込められる構成にはしていません。
  ホストからのハートビートが止まったときもドライブを切ります。
* **「このキットでなければ作れないか」を最後まで疑ったこと。**
  2値のロックならサーボで足ります。段階的な力の指令にしたのは、
  FOCの必然性を立てるためでもあります。

## 開発技術

### Infineon の技術で「感じて・考えて・返す」を一周させる

センサ・判断・アクチュエータのすべてを、Infineon のマイコンとセンサでつないでいます。
マイコンは2つ使い、役割を分けています。

| | 使った Infineon の製品・ツール | この作品での役割 |
|---|---|---|
| **感じる（Sense）** | PSOC™ Control C3（PSC3M5）の電流センシングと、モータ内蔵ホールセンサの読み取り（TCPWM / MOTIF） | ドアを開ける力と距離を、**ロードセルや角度センサを足さずに**測る。1回ごとに「どれだけの力で開けたか」をミリジュールで残す |
| | XENSIV™ 60GHz レーダー BGT60TR13C（PSOC™ Edge E84 AI Kit 上） | 手を合わせて「お願い」する動きを、カメラを使わずに感じ取る |
| **考える（Think）** | PSOC™ Edge E84 の Arm® Cortex®-M55 と AI 専用演算器 Ethos™-U55、DEEPCRAFT™ Studio のモデル | レーダーの波形から手の動きを、クラウドに送らずボードの中で判定する |
| | PSOC™ Control C3 の Arm® Cortex®-M33（FPU） | 開けた距離と速さから、ばね・粘り・粘り負けの強さを毎ミリ秒決める状態機械 |
| **返す（Act）** | PSOC™ Control C3 の FOC（ModusToolbox™ motor-ctrl-lib）と、Infineon のモータ駆動パワーボード KITMOTORDC250W24V | 電流＝トルクを直接指令して、「中くらいの力で押し返す」手応えをつくる |
| **開発環境** | ModusToolbox™（2つのボードのファーム）、KitProg3（E84 の書き込みとシリアル） | |

* 1台のモータキットが、アクチュエータであると同時に力のセンサにもなっています。
  「開ける力を測る」と「押し返す」を同じ部品で行えるのは、電流を直接扱う FOC だからです。
* AI の判定は E84 の中で完結し、レーダーなのでカメラ映像も残りません。冷蔵庫のように家の中に置くものに向いています。

### 独自技術

#### ハッカソンで開発した独自機能・技術

* **ドア抵抗制御ファームウェア** — [`motor-fw/door.c`](motor-fw/door.c) / [`motor-fw/door.h`](motor-fw/door.h)
  （commit `854a168`, `50266e7`, `b72a754`, `8446267`, `105256c`, `3e13402`）
  モータを「回す」のではなく「回されることに抵抗する」ために、
  ホール位置から開方向の動きを検出し、`level` に応じた電流を逆向きに流す。
  DISARMED / IDLE / RESIST / COOLDOWN の状態機械で、
  糸のたるみ取り、過速度、長時間の抵抗による発熱を管理している。
  * **手応えの形**：開けた距離に応じて強くなるばね、開ける速さに応じた粘り、
    開け始めの「ブルッ」という警告の振動
  * **人間っぽく粘り負けする**：強い力で1秒耐えたあと、4秒かけて力が抜けて最後は 0 になる。
    ドアは必ず最後には開く
  * **開けた記録**：1回開けるごとに、手がモータに対してした仕事（mJ）・最大電流・距離・時間・
    途中でやめたかを記録する（電流 × トルク定数 × 回転角）
  * **閉じた位置まで糸を巻き戻す**：一番巻き取った位置を「閉じた位置」として覚え、扉を閉めたあと
    軸がその手前で止まったら、短く強めに引いて巻き取りを再開させる。引いても近づかなければ
    （手で押さえている・開いたまま）3回でやめて待つので、扉を無理に閉めない

* **ホスト↔ファーム間のライブリンク** — [`host/door_link.py`](host/door_link.py)
  ELFからシンボルアドレスを解決し、J-Link経由で `door` 構造体を直接読み書きする。
  UARTを使わずにMCUを走らせたまま指令とテレメトリを扱える。
  ホストが心拍を送り続けないとドライブが切れるウォッチドッグを実装。
  電源や USB が抜けても自動でつなぎ直す。手応えの設定は取り付け方ごとの
  [`host/mounts/*.json`](host/mounts) にまとめ、`control.json` に書けば動作中に変えられる。

* **手を合わせて「お願い」する** — [`edge-fw/`](edge-fw) / [`host/gesture.py`](host/gesture.py)（commit `97ffaca`）
  E84 のレーダーと AI 専用演算器で手の動きを判定し、手を合わせて前に突き出す（Push）と、
  次の1回だけドアが軽くなる。カメラを使わないので、家の中でもプライバシーの心配が少ない。

* **タスクの重み付け** — [`host/fridge.py`](host/fridge.py)（commit `3869d92`, `92eeb79`）
  タスクの「重さ」を Claude が推定し、未完了の重みの合計からドアの重さを決める。

* **開けたあとの気持ちで、次の重さを変える** — [`host/reflect.py`](host/reflect.py) / [`host/fridge_gui.py`](host/fridge_gui.py)
  開け切るたびに「満足 / ふつう / 後悔」を1タップで記録し、その回の引いた力・時刻・残りタスクと一緒に残す。
  時間帯（昼 / 夜）ごとに最近5回の答えを見て、最大の力に 0.75〜1.25 倍をかける（上限 2.5A）。
  理由を画面に出せるよう、あえて単純な決まりにしている。段階（level）の決まり方は変えないので、
  寸劇の流れは崩れない。本番で動きを固定したいときは、画面のチェックで学習を止められる。

* **ブラウザで動くシミュレーター** — [`host/sim/`](host/sim)（commit `01d7657`）
  ファームの制御を JavaScript に移し、ドアと手の物理モデルと組み合わせて、
  実機なしで手応えの設定を試せる。

* **センサレスではなくホール位置検出を選んだこと**（commit `50266e7`）
  ドアを開ける動作はほぼゼロ速度域から始まるため、
  センサレスFOCでは回転子位置を推定できず保持トルクが出せない。
  SysTickでホールをサンプリングする構成に変更して解決した。

* **静止したまま力を出すと誤って止まる問題を回避**（commit `b72a754`）
  ドアを押さえて止まっている間は電流が流れても回転しないため、
  ライブラリが「相が外れた」と誤検知して停止していた。この検知を外し、
  それ以外の異常は2秒ごとに自動で解除して復帰するようにした。

## ハードウェアと動かし方

### 全体の構成

```
[ドア] ──糸── モータ軸（DB42M03）
                │ 動力線3本 ＋ ホールセンサ5本
[パワーボード KITMOTORDC250W24V] ── 24V AC アダプタ
                │ アダプタボード
[制御ボード KIT_PSC3M5_CC2]  motor-fw/door.c が電流を決める
                │ USB-C（J-Link）
[Mac]  run-string.sh（door_link.py） ← control.json ← fridge_gui.py ← tasks.json / weights.json
                │ USB-C（KitProg3 のシリアル）
[PSOC Edge E84 AI Kit]  edge-fw：レーダーで手の動きを判定
```

### 配線（作業は必ず 24V を抜いてから）

| どこ | つなぎ方 |
|---|---|
| 制御ボードのジャンパ X20 | 2-3 側（V5V）。制御ボードの電源をパワーボードから取る |
| 制御ボードの DIP スイッチ SW3 | すべて右側 |
| モータの太い線（動力） | パワーボードのネジ端子 CN3：黄 → U、赤 → V、黒 → W |
| モータの細い線（ホールセンサ） | 制御ボード X3：赤 +5V → 1、青 H1 → 2、白 H2 → 3、緑 H3 → 4、黒 GND → 5 |
| 24V AC アダプタ | パワーボードの CN1（丸い DC ジャック） |
| Mac | 制御ボードの USB-C（X10）。E84 は KitProg3 側の USB-C（J1） |

* 太い線と細い線の両方に赤と黒があります。取り違えるとボードやモータを壊すおそれがあります。
* USB は J-Link だけに電気を送ります。マイコンは 24V 側から動くので、24V が抜けるとボードは止まります。

### 機構（糸の取り付け）

* 糸はモータ軸に直接巻き付け、先をドアの取っ手側に結びます。糸巻きは使っていません。
* 軸が1カウント（15°）回ると、糸が約2mm出ます（巻いた太さで変わります）。
* 取っ手にかかる力は、2A のとき約10Nです（太めの糸の場合）。
* 軸に横からかけてよい力は、付け根から20mmの位置で最大28Nです。糸はなるべく付け根近くに巻いてください。
* ドアが閉まっている間は 0.2A で糸を巻き取って、たるまないようにしています。
  ただし止まった軸は 0.2A では回り出さないことがあるので、閉じた位置の手前で0.4秒止まったら
  0.6A で0.2秒だけ引いて回し始めます（効かなければ3回でやめて5秒待ち、それを3回くり返したら
  その位置を新しい閉じた位置とみなす）。
* 閉じた位置は電源を入れるたびに覚え直すので、**`run-string.sh` を起動するときは扉を閉めて糸を張っておいて**ください。

### デモの動かし方

Mac の窓は2つです。**必ず 1 → 2 の順に起動**してください。`run-string.sh` は、自分が起動する前に書かれた `control.json` を無視します。

```sh
cd host
./run-string.sh                                      # 窓1：ボードにつないで、手応えの設定を送る
uv run --python 3.11 --with pyserial fridge_gui.py   # 窓2：タスクの画面。チェックするとドアの重さが変わる
```

* `run-string.sh` は `host/.venv`（Python 3.9、pylink-square と pyserial）で動きます。
  作り直すときは `uv venv host/.venv && uv pip install --python host/.venv/bin/python pylink-square pyserial`。
* GUI は Python 3.11（uv が入れるもの、Tk 8.6）で動かします。macOS に付いている Python 3.9 の Tk 8.5 では、
  文字や色が描かれず、押したボタンも消えません。
* `weights.json`（タスクの重み）があると、重みの合計で段階が決まります。今の重み
  （レポート 0.9 / ストレッチ 0.2 / 持ち物 0.4）では、寸劇は
  **ストレッチ → 持ち物 → レポートの順にチェック**します。
  level は 1.00 → 1.00 → 0.50 → 0.00 と動きます。レポートを最初にチェックすると、いきなり 0.25 まで下がります。
* E84 がつながっていれば、GUI はレーダーで「お願い」を見張ります。
  E84 の表側（Infineon のロゴの面）の正面、約60cm から、手を合わせて20〜30cm 前に突き出すと、
  画面が「今回だけだよ」になり、次に1回開け切るまでドアが軽くなります（30秒で元に戻る）。
  判定の様子は窓2のターミナルに流れます。
* お願いを聞くのは **3時間に1回まで**です。それより早いお願いには「お願いは3時間に1回まで（あと○時間○分）」と出て、
  重さは変わりません。GUI を起動し直しても数え続けます（`host/logs/onegai.json`）。
  誤作動やリハーサルで使ってしまったときは、**本番の前に GUI の画面で Ctrl+R（⌘R でも可）** を押すとリセットできます。
* 開け切ると、画面に「食べてどうだった？」と3つのボタンが出ます（60秒で消える）。
  答えは `host/logs/feelings.csv` に残り、`python3 reflect.py` で日ごとの表にできます。
  別の CSV を渡せば（`python3 reflect.py sample.csv`）同じ形の表を出せます。
  学習で最大の力が変わると、画面の「最大 ○ A」とその理由が変わります。

### 手応えの設定（`host/mounts/string.json`）

| 項目 | 今の値 | 意味 |
|---|---|---|
| `take` | 0.2 A | 閉まっている間の巻き取り電流 |
| `max` | 2.0 A | level 1.0 のときの最大電流 |
| `free` / `ramp` | 0 / 12 カウント | 引き始めから重くなり始め、約2.5cm で最大になる |
| `damp` | 0.005 A/(カウント/秒) | 開ける速さに応じた粘り |
| `full` | 36 カウント | 約7.5cm 開けたら「開けた」として記録する |
| `buzzamp` / `buzzhz` / `buzzms` | 0.6 A / 40 Hz / 200 ms | 開け始めの「ブルッ」。level 0.5 以上のときだけ鳴る（`buzzlevel`） |
| `relentdelay` / `relent` / `floor` | 1秒 / 4秒 / 0 | 最大の力で1秒耐えたあと、4秒かけて 0 まで力を抜く |
| `recover` | 1.5秒 | 手を離したあと、元の強さに戻るまでの時間 |
| `release` | 3 カウント | ドアがこれだけ戻ったら「手を離した」とみなす |

`level`（0〜1）は GUI が決めます。タスクの状態から 0 / 0.25 / 0.5 / 1.0 の4段階になります。
設定は動作中でも変えられます。窓1に `ramp 20` のように打つか（日本語入力中は Enter を2回）、
`control.json` に `{"ramp": 20}` のように書いてください。

### 安全のしくみ

* 電流の上限は 3A（モータ定格 3.47A 未満）。電流は糸を巻き取る向きにしか流さないので、糸がドアを押すことはない
* Mac からの心拍が 0.5 秒止まると、モータへの電流を切る（Mac が落ちてもドアはただのドアに戻る）
* 抵抗を10秒続けたら、3秒休む（発熱対策）
* 巻き取りが毎秒400カウント（どちら向きでも毎秒1500カウント）を超えたら、速さが収まるまで電流を切る。
  糸が切れた・たるんだとき、手を離したときに、糸を勢いよく巻き込まないため
* 「ブルッ」の振動は 1A / 100Hz / 1秒が上限
* 電源が切れると軸は自由に回り、ドアは普通に開く

### ファームの書き込みと戻し方

```sh
cd motor-fw
make build
./flash.sh   # make program は "No PCode loaded" で失敗することがあるので、こちらを使う
```

* 書き込む前に `run-string.sh` を止めてください。J-Link は同時に1つのプログラムしか使えません。
* `run-string.sh` と `flash.sh` は、モータキットの J-Link を**シリアル番号で選びます**（このチームのキットは 591234791）。
  磁気センサーのキットも同じ名前の J-Link を持っていて、両方つながっていると取り違えるためです。
  別のキットでは環境変数 `DOOR_JLINK_SERIAL` に番号を入れてください（空にすると、つながっている J-Link を使う）。
* **今ボードに入っているのは、閉じた位置まで巻き戻す変更を入れた版です**（2026-10-25 13時台に書き込み）。
  `3e13402`（手を離したら糸を引き戻さない、手で押さえている間は粘り続ける）も、この書き込みで初めて入りました。
* デモ用の Mac には、その前まで使っていた `105256c` のファームのバックアップがあります
  （`~/Projects/jphacks2026-fw-backup/demo-ok/`、リポジトリ外）。新しい版で困ったときは、
  `restore.sh` で書き戻し、`verify.py` でボードの中身と1バイトずつ照合できます。

### E84（お願いのレーダー）

```sh
cd edge-fw

make build
```

* 中身は Infineon のコード例 `mtb-example-psoc-edge-ml-deepcraft-deploy-radar` です。
  レーダーの受信波形（5ミリ秒ごとに128個の数値）を、そのまま AI のモデルに入れています。

* 判定には約0.5〜1.2秒の遅れがあります。
* **限界**：形ではなく「何かが近づいて戻った」動きを見ているので、人が動き回る場所では誤作動が多いです。
  Circle は誰もいなくてもスコアが高く出るので、使っていません。

### うまく動かないとき

| 症状 | 原因と対処 |
|---|---|
| 窓1に `! lost the board` | 24V か USB が抜けた。挿し直せば自動でつなぎ直す |
| 窓1に `InitTarget() returned with error code -1` が続く | J-Link は見えているが、ボードに 24V が来ていない |
| GUI でチェックしてもドアの重さが変わらない | GUI を `run-string.sh` より先に起動した。GUI を起動し直すか、チェックを1回変える |
| 「お願い」が反応しすぎる・しない | E84 の向きと、正面で人が動いていないかを確認する。窓2のスコアで確かめられる |
| GUI に文字や色が出ない・押したボタンが消えない | macOS 付属の Python 3.9（Tk 8.5）で起動している。`uv run --python 3.11 --with pyserial fridge_gui.py` で起動する |

* ヒンジに取り付ける方式（`host/mounts/hinge.json`）は、設定だけ用意してあり、実機では試していません。
